# OpenCode Image to Code

Codex resolves project context, delegates implementation to OpenCode, and compares the rendered result with the original images. OpenCode owns visual implementation and visual corrections. The supplied images govern appearance throughout the task. Read [the worker prompt](references/worker-prompt.md) before delegation; read [usage examples](usage-examples.md) when invocation guidance is needed.

The reference defines the complete visual scope for both agents. Every visible element and styling decision must be supported by the image or an explicit user instruction. Similarity to an existing element provides no basis for substitution. Codex resolves technical integration and identifies discrepancies; visual additions, substitutions, improvements, and redesign require an explicit user request. Investigate unclear details and retain unresolved findings rather than inventing replacements.

## Resolve a minimal request

An attached image or image path is sufficient when the active project is known. Infer the framework, language, styling setup, route convention, package manager, and running application URL from project instructions, source files, configuration, and active runtime evidence. Implement within that stack and route convention; a standalone HTML document requires a matching project convention or explicit user request. Honor explicit destination, URL, framework, model, ignore regions, and additional instructions. Briefly state the inferred destination and URL before working. Ask only for information whose absence prevents faithful execution or leaves materially different targets equally plausible.

Read the target project's applicable instructions. Inspect the actual original images using an image-viewing tool. Resolve every reference to a local file OpenCode can open; conversation attachments alone are insufficient for a separate worker. Use attachment export/download capabilities when available. If an image cannot be transferred, request its local path or upload and keep the task pending. Confirm OpenCode actually opens each image with an image-capable tool and reports concrete visual observations before accepting its implementation.

Use image dimensions as initial capture dimensions, accounting for known device scale, browser chrome, and crop boundaries. For ambiguous crops or full-page references, resolve the viewport from available context and record uncertainty. Map multiple images to pages, states, or viewport sizes before delegation; clarify conflicting references. Keep the original image as the comparison authority in every round.

## Create a separate implementation

This section governs new reproduction and design-adaptation requests. An explicit request to resume or continue an existing implementation follows the resume workflow below.

Create a new standalone page with new source files and its own directly visitable URL path. Honor a supplied path; otherwise infer a descriptive unused slug such as `/design-preview/dashboard` from the reference. Check both file and route collisions and choose an unused suffix when needed. Return the full running-app URL and verify direct navigation and refresh with `agent-browser`. Preserve existing routes.

Create all visual components, markup, layouts, and styles from scratch for the reference. Existing UI components are excluded from reuse, including imports, wrappers, extensions, copied implementations, and restyled variants, regardless of their similarity to the reference. This applies to shared design-system components, existing page sections, and visual application shells. Existing runtime and routing provide technical hosting for the new page. Its rendered surface contains only the reference UI and explicit user additions; any navigation or shell shown in the reference is newly authored too. Keep styles scoped, isolate the page from inherited visual constraints, and preserve existing pages and user changes. An additive route registration or required asset/package change may touch an existing file; enumerate those exact integration files in the worker contract.

When the user explicitly requests applying a reference to an existing design, inspect the requested behavior and create a newly authored standalone candidate at its own URL. Preserve only the content, interactions, and data contracts requested for that adaptation. Treat an explicit request to swap in the candidate as authorization for that targeted integration. Until then, the original remains the active implementation. For ordinary reproduction, implement the supplied view; additional workflows and unseen states require an explicit request.

For image reproduction, use the reference's visible content. Existing-page content and behavior enter the candidate only through an explicit adaptation request. State that requested content choice in the contract. In adaptation mode, record content-driven differences such as text wrapping separately while matching the reference's visual treatment and hierarchy. Ask only when the request leaves the content choice materially ambiguous.

Match each supplied viewport. Keep layout mechanics needed to render those views within the reference's visual scope. Additional responsive designs and unseen layouts require an explicit request; fidelity claims cover the supplied references and compared states.

Assume the application is already running. Use its existing URL. Starting, restarting, or spawning an application instance is outside this workflow. Resolve an unreachable URL through read-only configuration/runtime inspection; request the running address when necessary. Lint, oxlint, typecheck, builds, and tests are outside this workflow. Use browser rendering and scoped source inspection for verification.

## Resume an existing implementation

Accept an explicit resume or continue request for a candidate created by any model, provider, tool, or developer. Infer the candidate files, existing URL, original reference images, exclusions, and prior task constraints from the request and available project evidence. A page path or URL plus an accessible reference is sufficient; previous session access and provider credentials are optional. Clarify the target when several candidates are equally plausible, and request the original reference if it cannot be recovered.

Continue the selected candidate in place, retaining its files, URL, and candidate-owned components/styles. This is the scoped exception to new-page creation and from-scratch generation. Preserve matching regions and unrelated user changes. The restriction on importing, copying, wrapping, or restyling unrelated existing UI still applies. Inspect any shared UI dependencies already present, and resolve required replacements within the candidate's authorized scope; shared-source changes require explicit scope.

Confirm the previous worker has stopped writing. Read and retain the starting contents of candidate and permitted integration files. Inspect current source and capture a fresh rendering before correction. Both agents establish actual image access and independent findings against the original reference; previous reports provide context, while current pixels establish remaining work. Record the resolved resume context in the complete worker contract, then enter the normal comparison loops directly.

Resume implementation state through source, images, and task evidence. For work from another provider, an unavailable session, or a changed worker model, start a fresh OpenCode session with that context. A compatible OpenCode session may be resumed explicitly using the invocation reference. Keep the default worker model and user overrides unchanged.

For an interrupted task with a documented loop budget, carry forward verified completed loops and the remaining budget. A new count supplied with the resume request applies to additional loops unless the user specifies a total. With an unknown prior budget, use the default minimum of three new loops and report historical counts as unknown. In every case, perform a fresh comparison; record selected, historical, and newly completed counts separately.

## Delegate through the existing transport

Invoke OpenCode through the bundled wrapper using [the invocation instructions](references/opencode.md). Codex owns orchestration and acceptance; OpenCode owns implementation and visual corrections. Always use the installed `opencode-no-plugins.ps1` launcher. Default to Muse Spark 1.3 Contributor (`opencode-go/muse-spark-1.3-contributor`). Honor another user-selected model by resolving its exact provider/model ID through the same launcher. An unavailable model or missing image capability requires user direction, with the selected model preserved.

Create a unique temporary task directory outside application source for UTF-8 contracts, worker responses, and round screenshots. Fill every field in [the worker prompt](references/worker-prompt.md), including absolute image paths, project context, allowed files, the running URL, browser session, and exact exclusions. Attach the original images and current rendered screenshots with the wrapper's `-Images` argument. Establish actual image access before implementation using the visual check in the invocation instructions. Every pass receives the complete contract; correction passes may resume the explicit session recorded by the preceding run.

Run one OpenCode pass at a time, including model discovery: the launcher regenerates shared profile and project-overlay directories. The worker uses Build mode and noninteractive permissions; its allowed-file list is an instruction boundary. Inspect actual edits and report unexpected changes while preserving them for review.

Read and retain the initial contents of the allowed existing integration files before delegation so their changes can be reviewed against the starting state. Confirm proposed new paths are unused. Capture worker output and exit status. Poll an active invocation while providing progress updates. After a timeout, establish whether the worker is still running and inspect partial edits before retrying; only one worker may write the candidate at a time. Repair a concrete invocation/context defect and retry once. A repeated invocation failure is an incomplete result.

Leave general delegation instructions and transport files intact. Workers operate only on the assigned task; commits, pushes, deployments, and further delegation are outside its scope.

## Run the selected comparison loops

Accept an optional positive whole-number loop count in ordinary language, such as `do 5 comparison loops` or `2 rounds`. Each loop includes comparison, correction where needed, and verification by both agents of the resulting rendering. Counts below three are valid. Initial generation and image-access checks are separate from this count. Record the selected count in the worker contract and progress updates. Clarify an invalid count before running comparisons.

With the count omitted, retain the default of at least three loops, continuing for visible mismatches while progress continues. With an explicit count, complete that many loops and report remaining differences at the limit. An explicit `at least N` requests a minimum instead of a fixed limit. Each loop covers all supplied targets:

1. Capture the actual candidate in `agent-browser --headed false` at the reference viewport and state; do not launch a visible browser or use a separate browser-control mechanism. Use a task-specific browser session and operate it sequentially across Codex and OpenCode. Wait for fonts and images to finish loading, match scroll position and theme, and save a fresh screenshot for each target. Read the installed `agent-browser` core usage guidance before browser operation.
2. Codex opens the original reference and the new screenshot with an image-viewing tool and records visible differences independently. Source, DOM, and worker summaries support diagnosis; the rendered images establish visual fidelity.
3. Invoke OpenCode for a read-only comparison with the original images, that same current rendering, source paths, and complete task constraints. Supply Codex's current findings only after OpenCode has returned its own region-by-region findings. Use a fresh review session when the implementation session contains proposed corrections or acceptance predictions for this capture. Record both reviewers' findings against the same screenshot, using location, expected appearance, observed appearance, and required correction; reconcile them against the pixels before sending the correction contract.
4. OpenCode corrects the identified differences, including in the last selected loop. Capture the updated rendering and have both agents compare that same capture with the reference in a verification-only pass. Verification belongs to this loop. Carry remaining differences into the next loop, or report them at the selected limit. With one loop, compare the initial implementation, correct it, and verify the result. Record screenshot paths, findings, and remaining differences in the temporary task record.

Every loop examines the complete reference: composition, typography, assets, spacing, color, borders, shadows, icons, and wrapping. Where the image already matches, record agreement with evidence and leave code intact; the jointly reviewed capture also serves as verification for that loop. Acceptance requires a rendering reviewed by both agents after the final edit. Apply the independent-findings sequence to verification too. Verification preserves application source and reference images while permitting evidence files in the designated directory. Its findings may also supply the next loop's initial comparison when the rendering remains unchanged.

Match scrollbar visibility to the reference; `agent-browser` hides native scrollbars by default, and `--hide-scrollbars false` at launch retains them when needed. Capture a stable reference state: match hover, focus, caret visibility, and animation position, and keep displayed data consistent between comparisons. Record any temporary capture controls and confine them to the preview session. Save unannotated PNG evidence. For pixel differences, use `agent-browser diff screenshot --baseline <reference> --output <evidence-file> --threshold 0` on aligned captures and record the threshold. Its usual threshold of `0.1` can hide subtle color differences. Interpret the result alongside the original images; a clean diff alone establishes insufficient evidence of fidelity.

Both agents inspect the whole screen and enlarged corresponding regions. Examine glyph shapes, text baselines, component bounds, padding, border thickness, icon geometry, shadows, and background colors, gradients, or textures. Use aligned overlays or difference images to investigate discrepancies and uncertain matches. Preserve the original captures; align comparison copies using the known viewport, scale, and crop, keeping layout offsets visible. Treat image-difference measurements as diagnostic evidence, with each discrepancy assessed against the reference.

Use `agent-browser` to inspect computed typography and font loading, alongside enlarged screenshots of the actual letterforms. `get styles` reports computed CSS; use `eval` to inspect `document.fonts` and resource-loading evidence when needed. Record declared styles, loading evidence, and visual observations separately. Compare glyph shapes, weight, style, line height, letter spacing, and wrapping against the reference. Computed CSS and loaded resources alone establish insufficient evidence of which font drew every glyph. Preserve any remaining font uncertainty in the findings and keep browser inspection within `agent-browser`.

Before accepting capture evidence, check the actual browser results for font readiness and image loading, computed typography for the differing text, and the paths of enlarged regions used for fine-detail review. A timed wait establishes elapsed time only. Tie loading claims to the observed results. Obtain missing evidence before deciding whether a difference is corrected; failed evidence collection remains an explicit obstacle.

Keep each observed mismatch, including small ones, in the existing round record until a fresh rendering demonstrates its correction. Both agents identify the regions examined and evidence supporting their findings. Codex independently checks OpenCode's correction claims against those pixels. Agreement between agents supports acceptance only alongside the image evidence. Keep these checks within the selected comparison loops.

Carry unresolved typography, icons, assets, visible data, and geometry into each correction contract. For each repeated mismatch, record the investigation performed, the specific correction attempted, and its observed result. Use corresponding enlarged regions and available font/asset information to resolve uncertain details. Generic replacement symbols remain mismatches. Large-layout progress leaves these other findings active, and the repeated-mismatch diagnosis below applies to them individually.

Complete the selected count even if an earlier round looks correct, subject to the interruption conditions below. Reaching a fixed limit with visible mismatches produces an incomplete fidelity report. Resolve disagreements by returning to the original pixels, region crops, and observed dimensions. Codex corrections must identify reference-backed differences; creative redesign and taste-based embellishment are outside the assignment.

Completion requires all supplied targets to match visually at their recorded dimensions, except explicit exclusions. Report the observable result precisely: visual agreement at the captured viewport is the claim the evidence supports. Unknown font identity, missing assets, or unresolved differences remain disclosed limitations, even if the result looks plausible. Human faces are excluded by default; preserve their frame, size, crop geometry, and surrounding layout. Apply any additional exclusions narrowly.

Each accepted region needs inspection evidence, with all observed mismatches resolved or covered by the explicit exclusions and content adaptation agreed for the task. A difference attributed to rasterization or screenshot compression requires evidence for that specific cause; unexplained differences remain open. Reaching the selected loop count changes the remaining work budget, while the fidelity requirement stays the same.

If the same difference remains unchanged after two consecutive correction attempts, diagnose the image access, viewport, font/asset availability, and worker context, then retry with corrected evidence if possible within the selected count. An unrecoverable prerequisite, repeated invocation failure, or persistent lack of progress ends with an incomplete report containing exact remaining differences and rounds completed. A failure to obtain visual evidence also means incomplete. Report the selected count alongside completed rounds when interruption prevents reaching it.

## Handoff

Return the candidate path and preview URL, number of completed rounds, final reference/render evidence paths, and remaining differences or exclusions. For resumed work, distinguish verified historical rounds from rounds completed in this run. Inspect changed files for scope, accidental replacement, and reuse of unrelated existing UI through imports, wrappers, copied markup, or shared component styles. Retain candidate-owned code in resume mode; correct unrelated UI reuse within the permitted scope, and request scope for changes outside it. Preserve screenshots and contracts needed to review an incomplete result. Describe swapping in the candidate only when requested; carry out an already-authorized swap and visually verify the resulting route.
