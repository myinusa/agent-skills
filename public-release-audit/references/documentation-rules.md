# Documentation rules

Before creating or editing Markdown, read the bundled [Markdown creation and editing rules](when-creating-editing-a-md-file-docs.md) and [meta-commentary cleanup protocol](meta-commentary-cleanup.md). Also read the supplied writing instructions and applicable project documentation rules, including their linked files. Discover relevant files through repository instructions and paths such as `docs/rules/`. Read the specific rules for public documentation, README content, and prose cleanup when present.

Use the rules below as the bundled baseline. Apply session instructions and supplied rule files according to their priority.

Apply the cleanup protocol within the selected mode and authorized scope. Audit mode records findings; remediation mode edits confirmed problems. Markdown reports follow the bundled writing rules in both modes.

## Durable documents

Write for the document's actual reader. Describe current behavior, accurate commands, supported features, configuration, and relevant limits. Keep private implementation discussions and correction history in external working evidence.

Use plain English, active verbs, affirmative sentences, and one stable name for each concept. Lead with the practical fact. Use headings and lists where they help the reader locate information. Keep each paragraph focused on a distinct useful point.

Keep statements factual and supported. Preserve technical identifiers, examples, frontmatter, paths, code blocks, and link targets unless remediation requires a specific change. Express uncertainty according to the evidence. Use quotation marks for actual quotations and syntax that requires them.

Remove duplicated explanations, filler, stock openings, sales language, unsupported opinions, theatrical conclusions, and chat-shaped offers. End at the last useful fact. In public project documentation, remove leaked drafting instructions and process commentary. Agent instructions remain legitimate content in skills, prompts, and protocols.

## Public documentation remediation

Check a claimed feature against code, tests, reachable behavior, or supplied accepted requirements before describing it as available. Carry useful public feature information from private planning material into the appropriate public document using accurate current wording.

Use portable examples and clearly marked placeholders. Replace machine-specific instructions with usable configuration guidance when the implementation supports it. Preserve meaningful operational limits and ownership information.

Match the project's document structure and voice. Keep edits proportionate to the verified release findings. Validate changed links, command names, configuration keys, and feature claims.

## Reports and replies

Lead reports with the release assessment. Include evidence, necessary actions, and material coverage limits. Give each finding a concrete location and effect. Group duplicates and omit empty sections, generic checklists, and speculative recommendations.

Keep replies short: the outcome, the report link, and any material unresolved decision. Add technical detail when it changes the user's decision or explains the verification result.
